# 2026-08-21

## Foco del día
SL-1477 Feature 7 — persistencia del ordenamiento de tarjetas del Kanban POR-USUARIO (laneSorts), BE + FE. Cierre de dos BLOCKs de review y verificación de un tercero que resultó moot.

## Cambios principales
- **laneSorts es la única pieza per-user** del config Kanban (el resto es compartido por tabla). Store PK=userId/SK=tableId + GSI tableId-index para cascade delete.
- **BLOCK #1 — config:null perdía laneSorts** (commit `42f4873cc`): el GET ahora lee laneSorts incondicional y los expone en top-level siempre; el FE los inyecta en el config efectivo aun sin config compartida.
- **BLOCK #2 — async-seed race → board CONTROLADO** (commit `098673731`): el seed de una-sola-vez con `useState` no re-sembraba cuando el GET async resolvía tras el mount (misma key → sin remount → sort descartado; reproduce en navegación tabla-a-tabla). Se volvió el `KanbanBoard` controlado (renderiza `config.laneSorts`, reporta vía `onLaneSortsChange`); el padre adopta el cambio inmediato + debounce del save.
- **Tests**: wrapper `ControlledBoard` + regression guard de hidratación asíncrona. KanbanBoard 73/73, BE Kanban 37/37, tsc limpio.
- **Fix comentario stale** de `key={tableIdParam}` (commit `4e32abb1c`, local).

## Decisiones
- Board **controlado** en vez de local-state-con-hydration-effect → única fuente de verdad, elimina la clase de bug de re-seed.
- **Reversibility BLOCK descartado:** el 2do adversarial (shadow) marcó pérdida de datos one-way porque el PR previo #2014 (`8d3e5a421`, en develop) persistía laneSorts en el config compartido. El reclamo es mecánicamente correcto, pero el usuario confirmó que **no hay datos reales** (feature en construcción) → sin migración ni fallback.

## Pendientes
- Nit no-bloqueante: el debounce timer de `handleLaneSortsChange` es un ref compartido entre tablas — ordenar A y cambiar a B en <600ms cancela el save de A. Bajo impacto; fix = flush al cambiar `tableIdParam`. Sin decidir.
- Push de `4e32abb1c` (quedó local). sam deploy a dev para round-trip.
