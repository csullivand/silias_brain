# Session: 2026-07-31 — SL-1545 fix PUT /role timeout (batch permission writes)

## Context
- **Branch:** `feat/SL-1545-role-batch-uodate` (sic: typo 'uodate' en el nombre de rama). Pusheada. HEAD `23815c70a`.
- **Ticket:** SL-1545 (relacionado). Bug reportado por Camila.
- **Goal:** Arreglar que PUT /permissions/role/{id} da 504 al editar PERMISOS (name/desc solo funciona bien). El cambio SÍ persiste en BD aunque el cliente ve error.

## Diagnóstico
- Síntoma: editar permisos → 504 Gateway Timeout (>30s), pero la BD SÍ refleja el cambio. Editar solo nombre/descripción = rápido.
- Causa: el handler `Roles/application/role/update.ts` hacía **N save() + M delete()** individuales (una llamada por permiso) + **N GetItems** para validar resource ids (`ResourceModel.findByIds` = Promise.all de findById) + invalidación de cache (Redis KEYS). Con un set grande (~90 permisos) = ~180 round-trips a DynamoDB desde localhost → excede el timeout del gateway. Los writes igual completan server-side → por eso persiste aunque diga que falló.
- Backend real: DynamoDB (AWSDynamoService) por defecto/cloud; MongoDB solo on-premise (DB.class elige por env). Los writes ya eran Promise.all (paralelos) pero el volumen + límites de sockets/latencia los serializa.

## Fix implementado (Phases 1 + 2 del plan)
**Phase 1 — batch writes (colapsa N save + M delete → 1 llamada batcheada):**
- `shared/interfaces/DBClient.interface.ts`: método opcional `bulkWrite({TableName, puts, deletes})`.
- `shared/clases/aws/AWSDynamoService.class.ts`: `bulkWrite` con **BatchWriteItem** (chunks de 25, reintenta UnprocessedItems con backoff, y **THROW si quedan sin procesar tras el budget** — fix de adversarial, NO silent drop).
- `shared/clases/MongoDB.class.ts`: `bulkWrite` con `collection.bulkWrite` (unordered, upsert por id).
- `shared/clases/DB.class.ts`: `protected bulkWrite` delega al client, con fallback per-item si el client no lo implementa.
- `Roles/domain/models/Permission.model.ts`: `PermissionModel.bulkApply(roleId, addResourceIds, deleteIds)` + wrapper instancia `applyBulk`.
- `Roles/application/role/update.ts`: reemplaza los 2 loops por un solo `bulkApply`.

**Phase 2 — batch reads:**
- `Roles/domain/models/Resource.model.ts`: `findByIds` ahora hace **1 findAll scan** del catálogo (pequeño/estático) en vez de N GetItems. También acelera role list (get.ts) + create.

**Neto:** ~180 round-trips → ~5. Request bien bajo el timeout. Contrato del endpoint, audit payload y filas resultantes SIN cambio.

Formato neutral `{TableName, puts, deletes}` para que sirva a ambos backends. deletes = key objects `{id}`. puts = items completos (upsert por id). Sin colisión de keys en un batch (puts = uuids nuevos, deletes = ids existentes distintos).

## Phase 3 (NO hecha)
Mover la invalidación de cache (Redis KEYS, gated ≤100 users sync) fuera del hot path. Se dejó fuera: el volumen de round-trips era el driver dominante. Si sigue lento tras esto, es el siguiente lever.

## PR review + adversarial
- Adversarial encontró **BLOCK real (correctness):** AWSDynamoService.bulkWrite hacía `break` tras 5 reintentos y **dropeaba UnprocessedItems sin error** → handler reportaba 200 + counts de audit con filas faltantes (regresión a false-success). **Arreglado: throw** si quedan unprocessed tras el budget.
- Tras el fix: PR review Approved ✅, adversarial 5/5 PASS.
- LOW (aceptadas): findByIds ahora solo matchea resources ACTIVE (via findAll status filter) → un id a resource inactivo daría 422; el return castea plain objects `as ResourceModel` (consumers solo usan .id/.name).
