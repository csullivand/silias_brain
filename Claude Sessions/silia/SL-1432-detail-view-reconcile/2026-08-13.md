## Work Log (step by step)

### Step 1: Reproduced & root-caused the "removed column reappears" bug
- **What:** With `USER_LEVEL_DETAIL_CONFIG:'true'` globally on, removing a property in Configure View saved on write but reappeared on reload. Reordering persisted.
- **Why:** Read-side `reconcile` (getTableById → `UserViewConfigResolver.reconcile` → `reconcileDetailView`) rule #2 re-appended EVERY visible column missing from the layout. So a deliberately-removed but still-visible (`table_view`) column got auto-re-added on next read. `hide`/`table` visibility columns were exempt (already tested).
- **Files:** `DynamicTables/domain/utils/detailViewLayout.ts`, `domain/services/UserViewConfigResolver.ts`, `application/Tables/get/getTableById.ts`, `application/Columns/patch/updateColumn.ts`.
- **Result:** Confirmed write path (`updateTable.ts:188`) persists correctly; only read reconcile re-adds. PRD Feature 3 says drag-out-to-sidebar = supported removal (property stays "Table & View"), so reconcile violated the PRD.

### Step 2: First fix — "created after last save" threshold
- **What:** Gate reconcile auto-add on a timestamp: only re-add columns created AFTER the layout's last save (genuinely new, Feature 4); leave removed ones out (Feature 3). Deliberate adds keep flowing through the write path (`syncLayoutOnVisibilityChange`).
- **How:** `LayoutColumn.createdAt` + `reconcileDetailView(config, columns, layoutSavedAt?)`; resolver passed `this.overlay?.updatedAt ?? globalSavedAt`; call sites pass `table.updatedAt`.
- **Verified:** `createdAt` persisted since first column-model commit (#451), so app-created columns all have it. Tests fail-without-fix confirmed.
- **Commits:** `379d3b13b`.

### Step 3: Adversarial-verify BLOCK — real bug in the first fix
- **What:** Threshold used `overlay.updatedAt` whenever ANY overlay row existed, but `resolveDetailView` uses the personal layout only when `overlay.detailViewConfig != null`. A visibility-only overlay (Show/Hide used, Configure View never) reconciled the GLOBAL layout with the personal overlay's timestamp → removed-from-global column could reappear. Same SL-1432 bug via a different path. Human reviewer flagged the same root smell (table.updatedAt bumps on rename/move).
- **Fix (root cause):** Gave the layout its OWN timestamp — added `DetailViewConfig.updatedAt`, stamped only when the layout is written (`updateTable.ts` + both visibility paths in `updateColumn.ts`). Reconcile uses `config.updatedAt`, falling back — only for pre-stamp rows — to a value that MIRRORS `resolveDetailView`'s exact condition: `overlay.detailViewConfig != null ? overlay.updatedAt : globalSavedAt`.
- **Commits:** `453dac312`.

### Step 4: PR-review nits
- **What:** (LOW-1) Reused a single `nowTimeStamp()` in updateColumn shared-visibility branch. (Main) Verified the "legacy overlay coupling" via visibility-only save CANNOT manifest: `UserViewConfigModel.saveVisibility()` has ZERO callers and the real per-user Show/Hide path co-writes `detailViewConfig` (stamps its own updatedAt). Added a guard comment on `saveVisibility()`. (LOW-2) Deliberately kept `(createdAt ?? Infinity) <= layoutSavedAt` — `<=` protects the primary removal guarantee.
- **Commits:** `44a3b538e`.

### Step 5: Unrelated discovery — listGrants Lambda `HandlerNotFound` in dev
- **What:** `Runtime.HandlerNotFound: listGrantsMin.listGrants.handler is undefined or not exported`.
- **Root cause:** webpack→esbuild build migration. Webpack (`libraryTarget: commonjs2`) nested `export const handler` sources under a key → handler string `xMin.x.handler`. esbuild (`format:cjs`, no re-nesting) emits FLAT `module.exports.handler` (PROVEN with a scratch probe). Templates still carry the webpack-era NESTED handler → `module.exports.listGrants` is undefined → error.
- **Blast radius (grep `Handler:\s*\w+Min\.\w+\.handler`):** Access/infrastructure/aws.template.yml lines 398/416/438/456/474 (5 grant fns) + DynamicTables/infrastructure/aws.template.yml lines 1729/1751/1779/1802/1831 (`indexMin.index.handler`).
- **Fix direction (NOT yet applied):** flatten to `xMin.handler`. Line 496 `processInvalidationMin.handler` already correct.
- **Note:** `scripts/ci/probe-handler-shape.js` documents the webpack nesting but its `findHandler` searches all keys, so it does NOT catch the nested-vs-flat template mismatch.
