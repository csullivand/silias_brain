## Análisis (resultado)
Doc completo con diagramas mermaid: [[projects/Escalacion Forzada Admin - Analisis y Plan]] (repo: `docs/escalacion-forzada-admin-analisis-y-plan.md`).

Hallazgos clave:
- **escalación == ticket** (`EscalationRecord`, DynamoDB `Escalations`). No hay entidad Ticket aparte.
- Hoy **solo se escala automáticamente** (LLM en `AIChatbotProcessContext.class.ts:1430`). No hay creación manual → gap.
- **El gate de horario vive SOLO en el evaluador** (`EscalationEvaluatorService:109-146` → `EscalationBusinessHoursService.isWithinBusinessHours`). `createEscalation` (`EscalationRecordService.ts:33`) **NO valida horario** → llamarlo directo ya ignora el horario.
- `assignToAgent` (`:192`) exige status `requires_takecontrol` → `in_progress`, setea `assignedTo`.
- Estados: `requires_takecontrol → in_progress → resolved` (+ `deferred_outside_hours`).
- Permiso actual de asignar: `agent.inbox.reassign`.

## Decisiones tomadas (para la feature)
- Permiso nuevo **`agent.inbox.force_escalate`** (ADMIN+; superadmin bypass).
- **Bloquear** la conversación (blockConversation:true) → bot deja de responder.
- Si ya hay escalación activa → **409**; el FE oculta el botón.
- Identidad **del token** (userId; userName a confirmar de claims o lookup).
- **+2 columnas** en EscalationRecord: `isForced` (bool) y `forcedBy`/`forcedByName` (inmutables, sobreviven handoff).

## Plan (qué implementar)
1. Modelo/interface: `isForced`, `forcedBy`, `forcedByName` (retrocompatible, default false).
2. Servicio `forceEscalateAndAssign()` = guard duplicado + createEscalation(forzada, bloquea) + assignToAgent(admin).
3. Handler nuevo `Assistant/application/Escalations/Lifecycle/Force/index.ts` (permiso, identidad del token, 409).
4. Permiso CASL `agent.inbox.force_escalate` a ADMIN.
5. Infra: ruta `POST /{chatbotId}/escalations/force` + **build entry**.
6. Tests (servicio + handler).
