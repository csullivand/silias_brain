- **Result:** 16 helper/processor tests green; tsc clean.

### Step 2: PR-review + adversarial BLOCKERS round 1 (both real, both fixed)
- **API Gateway enum (adversarial BLOCK):** `CreateOrgUserModel`/`PatchOrgUserModel` pinned `role: enum: [admin,supervisor,operator]` with `ValidateBody: true` → API GW 400'd custom roles BEFORE the Lambda. Removed the enum (Lambda owns role validity now).
- **CSV lowercasing (PR review Changes-required):** `ImportUsersModal.tsx:149` sent `role.trim().toLowerCase()` but `resolveRoleId` matches names case-sensitively → "QA Lead" → "qa lead" → role_not_found. Fixed: map CSV role to the **canonical** account name via `validRoleNames`. Regression test added.
- **Trim role** (LOW) in createOneOrgUser + patchOrgUser.
- **Files:** `User/infrastructure/aws.template.yml`, `ImportUsersModal.tsx` (+test), `orgUserCreation.ts`, `patchOrgUser.ts`.

### Step 3: Two MEDIUMs (batch import correctness)
- **Concurrent-chunk email race:** dedupe by normalized email BEFORE chunking (`batchImportUsers.ts`); in-file dups recorded as pre-skipped; `UserImportJobModel.create` counts them as processed so progress hits 100%. Residual cross-request race documented (User table has no email uniqueness key).
- **SQS retry double-count:** `incrementProgress` writes a `chunk_<index>` marker under `ConditionExpression: attribute_not_exists` and returns null on re-delivery; processor treats null as already-applied and re-reads job to still finalize. (`dynamoUserImportJobRepository.ts`, `processUserImport.ts`).
- Tests: new `batchImportUsers.test.ts` + processor idempotency tests.

### Step 4: adversarial BLOCK round 2 — DynamoDB CMK key policy
- **Infra BLOCK:** `UserImportJobTableKmsKey` had only the root `EnableIAMUserPermissions` statement, missing `AllowDynamoDBToUseTheKey` (Service: dynamodb.amazonaws.com, kms:Encrypt/Decrypt/ReEncrypt*/GenerateDataKey*/DescribeKey/CreateGrant, scoped via kms:ViaService + kms:CallerAccount). DynamoDB uses grants → without it the CMK SSE fails at deploy or throws runtime AccessDenied. Confirmed against Folders/Roles/Accounts. SQS CMK correctly stays root-only (matches Folders SQS key).
- **Per-row resilience** (non-blocking correctness): wrapped each row's createOneOrgUser in try/catch so one transient throw can't abort the chunk (which would retry + misreport). Test added.

### Step 5: user-role migration script
- **What:** `scripts/migrations/migrate-user-roles.ts` — superuser→superadmin, user→operator, seller→operator. Paginated scan, case-insensitive match, conditional write (won't clobber), idempotent, DRY_RUN. Documented as Group C1 in `scripts/migrations/README.md`.
- **Ran DRY_RUN on DEV** (sandbox 817389378997, table dev-app-silia-com-User): 105 scanned, 60 would migrate (53 superuser→superadmin, 5 user→operator, 2 seller→operator). Confirmed `seller`/`user` exist in real data (legacy, not in Role enum).
- **Ran REAL migration** (user said no backup): 60 migrated. Verified mariamendez@silia.com = superadmin. Re-run = 0 migrated (idempotent).

### Step 6: DEV 403 regression → assertRole god-mode gap (root cause + fix)
- **Symptom:** migrated superadmin got 403 on GET /user/management ("You do not have permission to perform this action").
- **Root cause:** `assertRole` (shared/middleware/requireRole.ts:198) does a STRICT allow-list check — never bypassed super roles (despite its doc comment). 39 handler allow-lists list SUPERUSER but not SUPERADMIN → migrating superuser→superadmin dropped users out of every allow-list. (assertPermission DOES bypass superadmin at line 141; the 403 body matches assertRole's buildForbiddenResponse, not the authorizer.)
- **Fix:** added super-role bypass to assertRole (SUPERADMIN/SUPERUSER → return null before allow-list; IMPLEMENTADOR stays scoped). One change fixes all 39 + future. New `shared/middleware/__tests__/assertRole.test.ts`. Verified gate-by-gate for listOrgUsers.
- **CAVEAT:** fix is code-only, NOT deployed → DEV still 403s until deploy (shared change rebuilds many Lambdas). Migration ran AHEAD of the deploy.
