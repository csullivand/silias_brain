## Síntomas reportados (en orden)

3. Escalaciones **duplicadas** cuando ya estaba escalada.

5. FE manda `conversationId = channelId` (antes de refresh) vs `conversationId = id real` (tras refresh).

## Causa raíz por síntoma + fix
1. **Guard `expectedStatus:'active'`** en `updateConversationActiveEscalation` bloqueaba el forzado sobre conversaciones `closed_by_inactivity`. Fix: en path forzado saltar guard + reactivar (`status='active'`) + reconciliar TTL (`closedAt=0`, `expirationTime` futuro). Commit del fix (cherry-pick `95e2a8fdd` → luego evolucionó).
2. **Adversarial BLOCK (data-loss):** reactivar dejaba `closedAt` viejo → `memoryTtlCleanup` (scan por summary, sin filtro status, ancla en closedAt) marcaba `expirationTime=now` → TTL nativo DynamoDB **borra la conversación entera**. Fix: limpiar closedAt + expirationTime futuro. `atomicUpdateEscalationState` +campo `expirationTime`.
3. **Duplicados:** idempotencia dependía de `conversation.hasActiveEscalation` (que quedaba desincronizado por los otros bugs). Fix (`df325e34e`): idempotencia por la **tabla de Escalaciones** (`findByConversation` → active) — fuente de verdad.
4. **CONVERSATION_NOT_FOUND:** el FE manda el **channelId**; el backend buscaba por `ChatConversation.id`. Fix (`cf9aeb512`): `resolveChatConversation` (por id, o por canal vía `Chat.findByChannelId → activeConversationId`); si no resuelve → 404 (no huérfana). **PERO** el Lambda no tenía `CHAT_TABLE` env ni IAM sobre `Chat` → seguía 404. Fix infra (`8370e1782`): +`CHAT_TABLE` env + `dynamodb:Query` sobre `Chat` en `RoleEscalationsLifecycle`.
5. **FE inconsistente:** items live/WS usan `id = channel` (sin `conversationId`); items de API traen `id` real. `conversationId = selectedItem.conversationId || selectedItem.id`. Es INOFENSIVO con el backend (resuelve ambos al mismo ChatConversation). Fix FE del botón (`60434378a`): ocultar "Manual escalation" si ya está escalada (`conversationState in_progress/require_takecontrol`).
