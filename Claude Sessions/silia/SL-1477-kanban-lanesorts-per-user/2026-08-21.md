## Work Log (step by step)

### Step 1: Contexto — reglas del feature
- Config de vista Kanban es COMPARTIDA por tabla, SALVO `laneSorts` (orden de tarjetas dentro de una lane) que es la ÚNICA pieza POR-USUARIO (Feature 7). Decisión revertida del usuario: "el ordenamiento SÍ se debe guardar, por usuario".
- Store per-user: PK=userId, SK=tableId, GSI `tableId-index` para cascade delete. Espeja RowFillRules/KpiPrefs.

### Step 2: BLOCK #1 — config:null perdía laneSorts (commit 42f4873cc, ya pusheado antes de esta sesión)
- **What:** El GET cortocircuitaba en `config === null` antes de leer laneSorts → una tabla ordenada sin config compartida guardada perdía el sort al recargar.
- **Fix:** `getKanbanViewConfig.ts` lee laneSorts INCONDICIONALMENTE y los expone en top-level SIEMPRE (`{ config, updatedAt, laneSorts }`), y los mergea en `config.laneSorts` cuando hay config. El FE inyecta laneSorts en el config efectivo aun en un board de defaults/primer-uso.

### Step 3: BLOCK #2 — async-seed race → board CONTROLADO (commit 098673731, pusheado)
- **What:** `KanbanBoard` sembraba su estado con `useState(() => ({...config.laneSorts}))` — initializer de una sola vez. El GET del config es async e independiente del mount del board; si el board monta ANTES de que resuelva el fetch, siembra con `{}` y NUNCA re-siembra (misma key → sin remount → initializer no re-corre) → el sort guardado del usuario se descarta silenciosamente. Reproduce determinísticamente en navegación tabla-a-tabla (navigate sin remount de página).
- **Fix:** Board ahora CONTROLADO — renderiza `config.laneSorts` directo (única fuente de verdad) y reporta cambios vía `onLaneSortsChange`. Se eliminó `useState` seed + `useEffect` de persist + `didHydrateRef`. `handleLaneSort` useCallback computa el mapa completo y lo reporta arriba.
- `DataViewsPlaceholder.handleLaneSortsChange` ahora hace `setKanbanLaneSorts(laneSorts)` INMEDIATO (re-render ordenado) + debounce del save (600ms). El path de hidratación del GET usa setKanbanLaneSorts directo (no se re-guarda).
- LOW fix: `getKanbanViewConfig.ts` tipó `laneSorts` como `KanbanLaneSorts` (era `Record<string, unknown>`).

### Step 4: Tests (parte de 098673731)
- `KanbanBoard.test.tsx`: se agregó wrapper `ControlledBoard` (espeja cómo la app cablea el board) para los 10 tests de interacción que renderizaban el board pelón esperando re-sort local.
- Se reescribió el test "read-only / no handler" honestamente: sin `onLaneSortsChange` el board muestra el control pero queda INERTE (no re-ordena, no crashea).
- Se agregó el regression guard EXACTO que pidieron los reviewers: montar con `config.laneSorts` vacío, re-render de la MISMA instancia (sin cambio de key) con mapa poblado → el board aplica el sort ("applies laneSorts that arrive AFTER mount, no key change").
- Resultado: **KanbanBoard 73/73**, **BE Kanban 37/37**. 2 fallas pre-existentes en DataViewsPlaceholder.test.tsx (`useFolderCrumbs is not a function`, del merge de develop — NO relacionadas, confirmado con stash).

### Step 7: Segunda adversarial verify (shadow) trajo un BLOCK de reversibilidad — RESULTÓ MOOT

Al pasar a per-user sin migración: (1) el GET spread-ea el laneSorts per-user vacío sobre `stored.config` → oculta el valor compartido; (2) el PUT compartido escribe `laneSorts: {}` → borra permanentemente.
- **Verificación (git + código):** el reclamo es MECÁNICAMENTE CORRECTO. A `8d3e5a421` el `validateKanbanViewConfig` sí validaba+persistía `laneSorts` en el config compartido (esa rev, línea 147). Y el GET actual `getKanbanViewConfig.ts:65` = `{ ...stored.config, laneSorts }` (spread después → sobrescribe). El PUT actual `kanbanViewConfig.ts:167` = `laneSorts: {}`.
- **PERO: el usuario confirmó que NO hay datos reales de lane sort — el feature todavía se está construyendo, nunca se deployó con datos de usuario.** El BLOCK era condicional ("pierde datos SI la versión compartida shipeó sorts reales") y esa condición es FALSA. → No se requiere migración/backfill/fallback.
